# Campus Drop 제휴업체·운영자 포털 백엔드 전달 계약

> 상태: 제품 정책 확정본을 바탕으로 한 **백엔드 구현 요청서** (2026-08-13, KST)
>
> 범위: 제휴업체 포털(`/partner/*`), 운영자 포털(`/admin/*`), 게임 완료 보상, 이벤트 보상, 탐험대 시작 게이트에 필요한 서버 계약이다. 공개 랜딩에는 관리자·에디터 링크를 노출하지 않는다. 이 문서는 현재 웹 프로토타입의 화면·목업이 권한을 보장하지 않음을 전제로 한다.

## 1. 반드시 지켜야 할 보안 경계

- 권한 판단, 업체 소속 판단, 쿠폰 발급·삭제, 게임 보상, GPS 근접 판정은 **모두 서버 권위**다. 브라우저의 route 가드, 숨긴 URL, localStorage/sessionStorage의 role 값은 보안 근거가 될 수 없다.
- `/partner/**`, `/admin/**`, `/admin/editor/**` 및 이를 지원하는 API는 매 요청마다 서버 세션과 역할·소속·활성 상태를 검증한다. 권한이 없는 리소스는 존재 여부를 노출하지 않는다.
- 포털 세션은 서버 저장형 불투명 세션 ID를 `HttpOnly; Secure; SameSite` 쿠키로만 전달한다. HTTPS 운영 환경에서만 `Secure`를 사용한다. JavaScript가 세션 값, 역할, 비밀번호 재설정 토큰을 읽거나 영속 저장해서는 안 된다.
- 쿠키 인증 mutation에는 Origin/CSRF 검증을 적용하고, CORS origin은 정확한 운영 웹 origin만 허용한다. credential 요청에 `*`를 쓰지 않는다.
- 세션은 발급 시점부터 정확히 24시간 후 만료한다. 유휴 만료는 적용하지 않는다. 비밀번호 재설정 완료·계정 비활성화·승인 취소 시 해당 계정의 모든 세션을 즉시 폐기한다.
- 초대·재설정 링크, 세션 ID, 비밀번호, PIN, GPS 원좌표는 로그·분석·URL query·오류 메시지에 기록하거나 반환하지 않는다.
- 아래 API 예시는 신규 계약의 권장 경로다. 모든 성공/실패 응답은 기존 envelope(`success`, `data`, `error`, `timestamp`, `traceId`)를 유지하고, 지원이 끝난 `X-Partner-Session`/`X-Admin-Session` 헤더 인증은 포털용으로 사용하지 않는다.

### 프런트엔드 한계

백엔드가 이 계약을 구현하기 전에는 프런트엔드만으로 인증·역할·데이터 격리·쿠폰 수량·감사 로그·GPS·세션 보안을 실제 보장할 수 없다. 화면에서 링크를 감추거나 페이지 이동을 막는 것은 UX일 뿐이며, 백엔드 보호가 배포된 뒤에만 포털을 실사용 상태로 간주한다.

## 2. 계정, 초대, 승인, 재설정

### 2.1 계정 모델

포털 principal은 플레이어 `users`와 분리하거나 명시적으로 계정 유형을 구분한다. 최소 데이터는 다음과 같다.

| 대상 | 필수 속성 | 상태 |
| --- | --- | --- |
| 운영자 계정 | `loginId`, `phoneNumber`, `role`, `password_hash` | `PENDING_APPROVAL`, `ACTIVE`, `INACTIVE`, `LOCKED` |
| 업체 계정 | `loginId`, `phoneNumber`, `storeId`, `password_hash` | `PENDING_APPROVAL`, `ACTIVE`, `INACTIVE`, `LOCKED` |
| 매장(store) | `name`, `address`, `phoneNumber`, `categoryId`, `active` | `ACTIVE`, `INACTIVE` |

- 업체 계정은 **매장 하나당 정확히 하나**다. 스타벅스 광주점과 서울점은 서로 다른 매장·서로 다른 업체 계정이며 데이터를 공유하지 않는다.
- 기존 `partners → partner_branches → partner_staff_profiles`의 다지점/직원 구조는 이 포털 모델과 다르다. 백엔드는 매장을 권한 소유 단위로 만들고 업체 계정과 1:1 제약을 둬야 한다. 여러 지점 조회·여러 직원 계정은 제공하지 않는다.
- 업체 계정은 자기 매장만 읽을 수 있고, 매장명·주소·전화번호를 수정할 수 없다. 전체 관리 또는 제휴업체 관리만 수정한다.
- 비밀번호는 최소 12자이며 대문자·소문자·숫자·특수문자 중 3종 이상을 포함한다. 저장은 강한 단방향 password hash(예: Argon2id 또는 현재 권장 파라미터의 bcrypt)만 허용한다.
- 동일 `loginId`의 누적 실패가 10회가 되면 1시간 로그인 잠금이다. 성공 로그인 시 실패 카운터를 초기화한다. 잠금 판단과 카운터 증감은 경쟁 상태가 없게 서버 트랜잭션/원자 연산으로 처리한다.

### 2.2 일회성 초대와 가입 승인

1. 권한 있는 운영자가 대상 역할·매장(업체만)·수신 연락 수단을 포함한 초대 링크를 발급한다.
2. 서버는 256비트 이상 난수 원문 대신 hash만 저장한다. 링크는 1회 사용이며 발급일 **KST 23:59:59.999**에 만료한다. 사용·철회·만료 후에는 동일한 일반 오류로 거절한다.
3. 링크에서 가입 정보를 제출한다. 업체 가입은 전화번호, 가게 이름, 가게 주소, 아이디, 비밀번호를 입력한다. 가게 이름·주소는 초대가 가리키는 매장과 서버에서 대조하거나 승인자가 검토할 수 있게 `PENDING_APPROVAL` 신청 정보로 보관한다.
4. 가입 완료만으로 로그인할 수 없다. 승인 권한자가 `ACTIVE`로 승인해야 한다. 거절/비활성화 계정은 로그인할 수 없다.

발급·승인 권한은 다음과 같다.

| 행동 | 전체 관리 | 제휴업체 관리 | 사용자 서비스 관리 | 업체 계정 |
| --- | :---: | :---: | :---: | :---: |
| 운영자 초대 발급·운영자 가입 승인 | 가능 | 불가 | 불가 | 불가 |
| 업체 초대 발급·업체 가입 승인 | 가능 | 가능 | 불가 | 불가 |
| 업체 계정 비활성화 | 가능 | 가능 | 불가 | 불가 |

### 2.3 비밀번호 재설정

- 전체 관리는 모든 포털 계정의 재설정 링크를 발급할 수 있다.
- 제휴업체 관리는 업체 계정의 재설정 링크만 발급할 수 있다. 운영자 계정에는 발급할 수 없다.
- 링크는 초대 링크와 동일하게 단회·당일 KST 자정 만료이며, 원문은 저장하지 않는다. 재설정 성공 시 기존 세션을 전부 폐기하고 새 비밀번호 규칙을 검증한다.

### 2.4 역할(RBAC)과 화면 경계

역할은 `SUPER_ADMIN`(전체 관리), `PARTNER_ADMIN`(제휴업체 관리), `USER_SERVICE_ADMIN`(사용자 서비스 관리), `PARTNER_STORE`(업체 계정)으로 고정한다. 하나의 포털 principal에 복수 역할을 부여할지 여부는 아래 결정 필요 항목을 따른다. 기본 구현은 단일 역할이다.

| 리소스/행동 | SUPER_ADMIN | PARTNER_ADMIN | USER_SERVICE_ADMIN | PARTNER_STORE |
| --- | :---: | :---: | :---: | :---: |
| 전체 운영 영역 조회·변경 | 가능 | 불가 | 불가 | 불가 |
| 제휴 매장·업체 계정·초대·승인·재설정 | 가능 | 가능 | 불가 | 자기 계정/매장 조회만 |
| 매장 카테고리·관심사 매핑 | 가능 | 불가 | 불가 | 불가 |
| 쿠폰·제안 생성/조회 | 가능 | 가능 | 불가 | 자기 매장 조회만 |
| 제안 수락·거절 | 조회/감사만 | 조회/감사만 | 불가 | 자기 매장 제안만 가능 |
| 제휴업체 공지 작성·발행·예약 | 가능 | 가능 | 불가 | 읽기만 |
| 사용자 공지 작성·발행·예약 | 가능 | 불가 | 가능 | 불가 |
| 게임 테마/미션 발행, `/admin/editor` | 가능 | 불가 | 가능 | 불가 |
| 감사 로그 조회 | 가능 | 불가 | 불가 | 불가 |

- `PARTNER_ADMIN`과 `USER_SERVICE_ADMIN`은 서로의 영역을 **조회도 할 수 없다**. 목록 endpoint만 막는 것이 아니라 ID 직접 조회·검색·집계·파일 접근에도 동일하게 적용한다.
- 업체 계정은 제안 수락/거절 외 쿠폰 변경, 새 쿠폰 생성, 공지 작성, 매장 정보 변경을 할 수 없다.
- 공개 랜딩, 공개 사이트맵, 공개 CTA, 공개 내비게이션에는 `/admin`, `/admin/editor`, 미션 에디터를 노출하지 않는다. 이는 인증의 대체물이 아니다.

## 3. 매장 카테고리와 관심사 연결

- 매장당 카테고리는 정확히 하나다. 예: 카페, 식당, 볼링, 보드게임. 복수 카테고리는 지원하지 않는다.
- `SUPER_ADMIN`만 카테고리를 생성·수정·삭제하고, 관심사별로 갈 수 있는 업체 카테고리를 설정한다. 예: `커피` 관심사 → `카페` 카테고리.
- 하나라도 매장이 연결된 카테고리는 삭제할 수 없다. 먼저 모든 매장을 다른 카테고리로 옮겨야 하며, 서버는 `409 CATEGORY_IN_USE`로 막는다.
- 카테고리-관심사 연결은 가중치를 갖지 않는다. 쿠폰 추첨에서 같은 후보 쿠폰은 모두 같은 확률이다.
- 필요한 엔티티: `store_categories`, `interest_store_categories(interest_id, category_id)`, `stores(category_id not null)`. `interest_id`는 기존 관심사 마스터의 안정 ID를 사용하며 화면 표시명으로 조인하지 않는다.

## 4. 쿠폰, 제안, 방문자 집계

### 4.1 쿠폰 카탈로그와 수량

쿠폰은 매장에 귀속되며 다음 불변 필드를 가진다.

| 필드 | 규칙 |
| --- | --- |
| `name` | 새 쿠폰 제안 시 지정. 승인 후 수정 불가 |
| `benefitDescription` | 새 쿠폰 제안 시 지정. 승인 후 수정 불가 |
| `quantityType` | `UNLIMITED` 또는 `LIMITED` |
| `totalIssueLimit` | `UNLIMITED`면 null, `LIMITED`면 양의 정수. 플레이어에게 발급 가능한 총 장수 |
| `issuedCount` | 개인 쿠폰 발급 성공 시 증가. 만료·미사용이어도 되돌리지 않음 |
| `redeemedCount` | 매장 사용 완료(`USED`/`COUNTED`) 때만 증가 |
| `remainingIssueCount` | `LIMITED`에서 `totalIssueLimit - issuedCount`; `UNLIMITED`는 무제한 |
| `status` | `ACTIVE`, `DELETION_PENDING`, `DELETED` 등 화면용 투영. 실제 발급/사용 허용은 서버 상태 전이로 결정 |

- 발급 수량과 사용 수량은 반드시 분리한다. 수량 제한 개인 쿠폰이 만료되어도 발급 수량은 복구하지 않는다.
- 대부분의 일반 쿠폰은 무제한이며, 수량 제한 쿠폰은 특별 이벤트 전용이다.
- 삭제가 수락되기 전 `DELETION_PENDING` 쿠폰은 계속 발급·사용할 수 있다. 수락 순간 신규 발급을 중단하고, 이미 발급됐으나 미사용인 개인 쿠폰도 즉시 `REVOKED`로 만들어 PIN 사용을 막는다. 발급/사용/방문자/감사 이력은 지우지 않는다.
- 기존 개인 PIN QR 사용 계약은 유지한다. 실제 매장 사용 완료 시에만 방문자 1건으로 센다. 이는 unique user 수가 아니라 **사용 완료 쿠폰 건수**다.

### 4.2 운영자 제안과 업체 수락

제휴 쿠폰 변경은 `SUPER_ADMIN` 또는 `PARTNER_ADMIN`이 제안하고 `PARTNER_STORE`가 수락/거절해야 한다. 업체에게는 외부 알림을 보내지 않고 대시보드의 검토 대기 목록에서 표시한다.

| 제안 유형 | 운영자 입력 | 수락 시 효과 | 거절 시 |
| --- | --- | --- | --- |
| `CREATE` | 쿠폰명, 혜택 내용, 숫자 수량 또는 무제한 | 새 쿠폰 활성화 | 종료 |
| `CHANGE_QUANTITY` | 숫자 수량 또는 무제한 | 수량 설정만 변경 | 종료 |
| `DELETE` | 대상 쿠폰 | 위 삭제 규칙 적용 | 종료 |

- 쿠폰명과 혜택 내용은 기존 쿠폰에서 수정 불가다. 기존 쿠폰에 가능한 제안은 수량 변경과 삭제뿐이다.
- 같은 쿠폰에는 `PENDING` 제안이 하나라도 있으면 수락 또는 거절 전까지 새 제안을 만들 수 없다(`409 COUPON_PROPOSAL_PENDING`). `CREATE`는 매장 단위의 동시 제안 정책을 별도 결정한다.
- 업체의 거절은 사유 입력 없이 버튼 한 번으로 처리한다. 거절된 쿠폰 제안은 즉시 종료 상태이며 수정·재제안·재발송·재개할 수 없다.
- 수락/거절은 현재 활성 업체 계정의 해당 매장 제안만 가능하며, 상태 전이와 카탈로그 변경은 하나의 트랜잭션으로 처리한다. 반복 요청은 원래 결과를 안전하게 반환한다.

### 4.3 업체 대시보드와 쿠폰 현황

업체 대시보드는 자기 매장에 한해 다음을 제공한다.

- 오늘 방문자 수: KST 오늘 00:00부터 현재까지의 사용 완료 쿠폰 건수
- 이번 달 방문자 수: KST 매월 1일 00:00부터 현재까지의 사용 완료 쿠폰 건수
- 누적 방문자 수: 전체 사용 완료 쿠폰 건수
- 검토 대기 제안 수와 목록, 최근 제휴업체 공지
- 쿠폰 목록: 쿠폰명, 혜택 내용, 총 수량(숫자/무제한), 발급 수량, 사용 완료 수, 남은 발급 가능 수량, 상태

날짜 집계는 서버에서 `Asia/Seoul`을 기준으로 한다. 기존 `partner_dashboard_stats`가 `partner_id`와 `COUNTED` 사용량만 갖는 경우, 단일 매장 모델과 위 기준으로 마이그레이션/재집계가 필요하다.

### 4.4 개인 쿠폰 만료

- 매장 쿠폰 카탈로그는 삭제 승인 전까지 계속 활성일 수 있지만, 플레이어에게 발급된 개인 쿠폰에는 기한이 있다.
- 무제한 쿠폰 개인 발급분: 발급 당일 KST 23:59:59.999까지 사용 가능.
- 수량 제한 쿠폰 개인 발급분: 발급일을 포함해 3일째 KST 23:59:59.999까지 사용 가능. 예: 8월 13일 발급 → 8월 15일 자정 직전 만료.
- 만료 시 `AVAILABLE → EXPIRED`로 전이하며, 발급량은 반환하지 않는다.

## 5. 게임 완료·탐험대·이벤트 보상

### 5.1 일반 탐험대 게임 보상

- 탐험대에 합류하려면 구성원 사이에 적어도 하나의 공통 취미 또는 관심사가 있어야 하며, 서버가 가입·초대 수락 때마다 교집합을 다시 검증한다.
- 게임 완료 보상 후보는 플레이어의 전체 개인 취향이나 공통 취미가 아니라, **완료한 탐험대의 공통 관심사**에 연결된 카테고리만 쓴다. 공통 취미는 탐험대 합류 요건에는 사용될 수 있으나 쿠폰 후보 선정에서는 제외한다.
- 공통 관심사 → 연결 가능한 매장 카테고리 → 그 카테고리 매장의 `ACTIVE + UNLIMITED` 쿠폰 순으로 후보를 찾는다. 중복된 경로로 발견된 같은 쿠폰은 한 번만 후보에 포함한다.
- 후보 쿠폰 한 장마다 동일 확률이다. 카테고리별·관심사별 가중치는 없다.
- 탐험대 게임을 완료할 때마다 플레이어에게 개인 쿠폰 1장을 반드시 발급한다. 같은 게임을 다시 완료하면 다시 1장을 발급할 수 있다. 이 정책을 지원하려면 현재 `theme_completions(user_id, theme_id)`의 단일 완료 기록과 별도로 회차별 완료/보상 원장을 둬야 한다.
- 완료 이벤트의 재전송이나 동시 요청은 동일 완료 회차에 개인 쿠폰을 두 장 발급하지 않도록 idempotency key와 유니크 제약으로 막는다.

### 5.2 이벤트 게임·수량 제한 쿠폰

- 이벤트는 KST 시작·종료 시각을 갖고 이벤트 게임과 수량 제한 쿠폰을 직접 연결한다.
- 이벤트 기간 밖에서는 이벤트 게임을 플레이 목록에서 숨기고, 새 이벤트 보상도 발급하지 않는다. 이미 발급된 개인 쿠폰은 자신의 만료 시각까지 유지한다.
- 이벤트 게임의 해당 플레이어 첫 완료이고 연결된 수량 제한 쿠폰에 남은 발급 수량이 있으면 그 이벤트 쿠폰 1장을 발급한다.
- 같은 플레이어의 두 번째 완료부터는 일반 탐험대 보상 규칙의 무제한 쿠폰 1장으로 전환한다.
- 수량 제한 이벤트 쿠폰이 전체 소진되면, 모든 플레이어에게 일반 탐험대 보상 규칙의 무제한 쿠폰 1장으로 전환한다. 게임은 계속 플레이할 수 있다.
- 이벤트 게임 완료도 회당 개인 쿠폰은 1장만 발급한다. 제한 쿠폰 발급은 행 잠금/원자적 조건부 update로 총 발급 한도를 절대 초과하지 않는다.

### 5.3 탐험대 모집·체크인·노쇼

- 게임 제작 시 최소·최대 참여 인원을 각각 설정한다. 탐험대 생성은 게임별 범위 안에서만 허용한다. 현재 OpenAPI의 `minMembers=2` 고정과 `maxMembers`만 있는 모델은 변경이 필요하다.
- 탐험대 모집에는 시작 일자·시각(KST 해석)이 필수다. 시작일 전날 KST 23:59:59.999에 최소 인원을 검사해 미달이면 자동 취소한다.
- 위 마감 뒤에도 시작 전까지 추가 모집은 가능하되 최대 인원을 넘을 수 없다. 마감 이후 탈퇴 등으로 최소 인원 미만이 되는 즉시 자동 취소한다.
- 체크인 창은 모임 시각부터 1시간이다. 예: 19:00 모임이면 20:00까지. 모든 현재 확정 멤버가 성공 체크인해야 한다.
- 체크인 버튼을 누르는 순간에만 GPS 근접을 검사한다. 성공하려면 다른 성공 체크인 멤버들과 서로 50m 이내여야 한다. 충분히 가깝지 않으면 체크인 완료로 기록하지 않고 사용자가 다시 눌러야 한다. 게임 시작 직전의 별도 지속 위치 추적은 하지 않는다.
- 체크인 창 안에 전원이 성공 체크인하면 서버가 게임 시작 가능 상태를 자동 확정한다. 현행 HOST의 별도 시작 버튼/15분 창 계약은 이 정책과 맞지 않아 변경이 필요하다.
- 모임 시각 1시간 후에도 전원 성공 체크인과 50m 근접을 충족하지 못하면 탐험대는 자동 취소한다. 성공 체크인하지 못한 멤버만 `NO_SHOW`, 성공한 멤버는 노쇼가 아니다.
- 노쇼는 라이선스 영구 박탈로 이어진다. 웹은 라이선스 복구를 제공하지 않으며 복구는 iOS/기존 백엔드의 이미 결정된 절차만 따른다.
- GPS 원좌표는 응답·로그·분석·장기 DB에 저장하지 않는다. 50m 판정을 신뢰할 수 있게 만들 위치 증명/일시 보관 방식은 아래 결정 필요 항목에서 확정한다.

## 6. 공지와 감사 로그

### 6.1 공지

| 공지 종류 | 작성·발행 권한 | 노출 대상 | 상태 |
| --- | --- | --- | --- |
| 제휴업체 공지 | `SUPER_ADMIN`, `PARTNER_ADMIN` | 해당/전체 업체 포털 | `DRAFT`, `SCHEDULED`, `PUBLISHED` |
| 사용자 공지 | `SUPER_ADMIN`, `USER_SERVICE_ADMIN` | iOS/AOS 앱 API만 | `DRAFT`, `SCHEDULED`, `PUBLISHED` |

- 공개 웹 랜딩에는 사용자 공지를 표시하지 않는다.
- 공지는 임시저장, 즉시 발행, 예약 발행을 지원한다. 예약 시각은 `Asia/Seoul`을 기준으로 입력·표시하고 UTC instant로 저장한다.
- 서버 scheduler가 예약 시각에 원자적으로 `PUBLISHED` 처리한다. 웹 클라이언트가 열려 있어야만 발행되는 구조는 허용하지 않는다.

### 6.2 감사 로그

- 모든 민감한 포털 행위(초대/가입 승인/비활성화/재설정 발급, 로그인 잠금, 매장·카테고리·관심사 연결, 쿠폰 제안/수락/거절/삭제, 공지 상태 전이, 게임 발행, 라이선스 제재)를 append-only 감사 로그로 남긴다.
- 최소 필드: `actorId`, `actorRole`, `action`, `resourceType`, `resourceId`, 대상 매장 ID(해당 시), 결과(`SUCCESS`/`DENIED`/`FAILED`), `occurredAt`, 안전한 details, `traceId`.
- 감사 로그는 수정·삭제 API를 제공하지 않고 `SUPER_ADMIN`만 조회한다. 생성 후 3년간 보관하고, 3년 경과분은 백엔드 보존 정책에 따라 삭제한다.
- 비밀번호, 세션/링크 원문, PIN, GPS 원좌표, 불필요한 개인정보는 `details`에 넣지 않는다.

## 9. 결정 필요 (구현 전 확인 필요)

아래는 사용자 정책으로 확정되지 않았거나 현행 구조와 충돌해 기술 선택이 필요한 항목이다. 백엔드/프런트엔드는 임의로 결정하지 않는다.

1. **운영자 가입 정보**: 업체 가입은 전화번호·가게명·주소·아이디·비밀번호가 확정됐다. 운영자 초대 가입에도 가게명·주소를 입력할지, 아니면 전화번호·아이디·비밀번호만 입력할지 확정이 필요하다.
2. **포털 principal의 복수 역할**: 한 운영자 계정이 `PARTNER_ADMIN`과 `USER_SERVICE_ADMIN`을 동시에 가질 수 있는지, 아니면 역할 하나만 가능한지 결정이 필요하다. 이 문서는 단일 역할을 기본으로 한다.
3. **새 쿠폰 제안 동시성**: 같은 매장에 새 쿠폰 `CREATE` 제안을 여러 개 동시에 보낼 수 있는지, 매장당 하나의 pending create만 허용할지 결정이 필요하다. 기존 쿠폰은 쿠폰당 하나의 pending 제안으로 확정됐다.
4. **일반 게임 보상 후보 공백**: 정책상 일반 게임 완료마다 쿠폰 1장은 반드시 존재한다. 공통 관심사에 매핑된 활성 무제한 쿠폰이 0개인 경우 서버가 게임 시작/발행/관심사 연결 변경 중 어느 시점에 막을지 운영 규칙이 필요하다. 무관한 쿠폰으로 fallback하면 안 된다.
5. **이벤트-쿠폰 연결 cardinality**: 현재 문서는 이벤트 하나 ↔ 수량 제한 쿠폰 하나로 썼다. 이벤트에 여러 제한 쿠폰을 연결할 필요가 있는지 결정이 필요하다.
6. **GPS 50m 판정 증거**: 원좌표를 장기 저장하지 않으면서 순차 체크인한 전원이 서로 50m 이내였음을 어떻게 검증할지(신뢰 위치 검증 서비스/서명된 짧은 증명/휘발성 메모리 보관 기간) 보안·개인정보 설계가 필요하다. 단순 클라이언트 bool은 허용되지 않는다.
7. **게임 최소 인원의 허용 범위**: 게임 제작자가 최소 1명을 설정해 1인 게임을 만들 수 있는지, 혹은 현행처럼 최소 2명인지 결정이 필요하다. 최대 인원의 상한도 현행 20을 유지할지 확인이 필요하다.
8. **라이선스 영구 박탈의 시스템 연결**: 노쇼 1회 즉시 영구 박탈을 기존 entitlement/access restriction 중 어느 권위 데이터에 기록할지, iOS/백엔드의 복구 절차가 어떤 상태 전이를 기대하는지 기존 정책과 정합성 확인이 필요하다.

## 10. 구현·검증 체크리스트

- [ ] 신규/변경 API와 enum을 OpenAPI에 명시하고 권한별 401/403/404/409 테스트를 추가한다.
- [ ] 다른 매장 ID를 path/query/body로 주입해도 업체 계정이 타 매장 데이터·제안·통계를 읽거나 바꾸지 못함을 통합 테스트한다.
- [ ] 브라우저 저장소의 role 값을 바꿔도 서버 권한이 변하지 않음을 E2E로 확인한다.
- [ ] 초대/재설정 링크의 단회성, KST 자정 만료, 승인 전 로그인 거부, 10회 실패 1시간 잠금, 재설정 뒤 전체 세션 폐기를 테스트한다.
- [ ] 쿠폰 제안 수락/거절의 동시 요청, 제한 수량 끝 경합, 삭제 수락 뒤 미사용 grant revoke, 만료 뒤 issued count 미복구를 테스트한다.
- [ ] KST 날짜 경계(자정, 월초, 이벤트 종료, 개인 쿠폰 3일째)를 고정 clock 테스트로 검증한다.
- [ ] 탐험대 전날 마감·탈퇴 후 즉시 취소·1시간 체크인 종료·성공/실패 멤버 노쇼 구분·50m 경계를 테스트한다.
- [ ] 감사 로그가 민감 원문을 담지 않고 3년 보존/삭제 정책에 맞는지 검증한다.
